# Comparison Architecture（Mobile Comparisonを含む）

## 1. Comparisonの定義

Comparisonは「2つのテキストを分析する画面」ではなく、**「2つの翻訳を同じBible Locationとして読む環境」**である。ReadingState の一状態であり、Research（分析・深掘り）ではない。翻訳差分分析ツール、翻訳評価ツール、Research Dashboard、Diff Viewerのいずれでもない。

- **Translation A** — 現在読んでいる翻訳
- **Translation B** — 比較用に選択した翻訳

v1は2翻訳のみ。3つ以上のグリッド表示は行わない（§4 Avoidを参照）。

## 2. 既存実装との差分（設計上の最重要な訂正点）

実機で「比較表示」を検証した結果、現状のComparisonは次のようになっていた：

- 「左列／右列」という発想は既に存在するが、各列の中身が「現在の翻訳（口語訳）」と「4つのView Mode（語順／構造／文の役割／つながり）」という**同一の平坦なリスト**から選ぶ形になっている。つまり現状の「Comparison」は実質、"Default表示 と 任意のView Modeの2ペイン分割" であり、**2つの異なるTranslationを並べて読む機能ではない**。
- 真の翻訳間比較（例：口語訳 と 新改訳2017）は、「外部の翻訳で比較」という別セクションから、**外部サイトを新しいタブで開く**ことで実現しており、アプリ内では同じ画面に2つの翻訳が並ばない。同期は「語順フロー」でのみ行われる、という説明がある。
- これは歴史的な暫定実装であり（Existing UI ≠ final design）、本Design Systemが再設計すべき中心的なギャップである。

### 2.1 再設計の方向

Comparison Setup UIを、Translation選択とView Mode選択が独立した2段階の選択として再構成する：

```text
Comparison Setup
├── Translation A: [ 現在の翻訳 ]（固定 or 変更可）
├── Translation B: [ 翻訳を選択 ]  ← 翻訳一覧から選ぶ。View Modeの4項目とは別リスト
└── 各列の見え方（任意）: Default / WORD_ORDER / STRUCTURE / CLAUSE_ROLE / RELATION
      各Translationペインは、Translationとは独立にView Modeを持てる
      （例: A=口語訳のDefault、B=ギリシャ語原文のWORD_ORDER）
```

これにより、既存の「左列に構造で読む」という使い方（Translation×View Modeの組み合わせを比較する）も、真の翻訳間比較（Translation A×Translation B）も、**同じ1つの仕組みの特殊ケースとして両方成立する**。「外部の翻訳で比較」機能は、既存Search/Data Architectureを変更しないという制約（`09`）の範囲で、段階的にアプリ内Translation Bとして取り込むことを推奨する（実装優先度は `09-implementation-priorities.md`）。

## 3. Comparison Synchronization

同期の基本単位は **Verse / Bible Location** であり、pixel-perfect scrollingではない。翻訳によって文章量・改行・行長・フォント・レイアウトが異なるため、「同じスクロール位置」ではなく「同じBible Location」を同期対象とする。目的は、両方の翻訳で同じ聖書箇所を読めることであり、行の高さを揃えることではない。

実装イメージ：各Verseブロックに `data-verse` を持たせ、片方のペインをスクロールしたとき、もう片方は「現在最も画面中央に近いVerseと同じVerse」が同程度の位置に来るよう追従する（アニメーションの値は `10-motion.md` を参照、控えめに）。完全な行同期は目指さない。

この「追従」は、左右2ペインが別々のスクロール領域を持つDesktop Comparisonを想定した記述である。Mobile Stacked Comparison（縦積み・単一スクロール）は構造そのものが異なり、常時追従の仕組みを持たない——詳細は §5.3・§5.6 を参照。

## 4. Comparison UX原則

- Bible Textが常に前景。ControlsはBible Textより視覚的に軽く。
- Shared context（今どのBible Locationを両方が読んでいるか）は常に明示——breadcrumbのBible Location表示はComparison中も1つだけ（Translation AとBで別々のbreadcrumbを出さない）。
- Translation選択の重複を避ける——Comparison Setupは1つの入口（`ReadingStateSwitch` → Comparison → Translation A/B選択）に集約し、各ペインの中に個別の翻訳セレクタを常設しない（既存実装が左右列内に同じ選択肢を繰り返す構造は避ける）。
- 過度なDiff Highlightingを避ける。単語単位の色分け差分表示は行わない——2つの翻訳は「違いを見る」ためではなく「両方を読む」ために並んでいる。
- 複数翻訳グリッド、複雑な比較コントロール、データテーブル化を避ける。
- v1は **Readable Bible first. Comparison second.**——Comparison Surfaceであっても、個々のTranslationペインは単独のSingle Readingとほぼ同じ見た目・組版であるべきで、「比較専用の特殊な組版」を新たに作らない。
- **列幅の最小可読幅（新規・実装未確認）**：実機調査で、比較表示の列幅に最小可読幅の下限が定義されていないことを確認した。本Design Systemはこれを設計要件として定める——各Translationペインの幅がMeasure（`05`§8）を維持できないほど狭くなる場合は、列を圧縮し続けるのではなく、Desktop 2ペイン横並びからStacked Reading（Mobile Comparisonと同じ構造）へレスポンシブに切り替える。等分割の`1fr 1fr`のようなグリッドだけに依存しない。具体的なブレークポイント・下限値は`05`§8の実測後に確定する。

## 5. Mobile Comparison — 最重要Representative Screen

### 5.1 出発点の再設定

問うべきは「現在の比較UIをどう改善するか」ではなく、**「このProductにおいて、MobileでComparison Readingとは何か」**である。

スマートフォンだけで聖書を読むユーザーにとって、Mobile Comparisonは妥協版ではなく **正当なPrimary Reading Environment** である。実機確認では、現状モバイルの「読み方」シートにComparison切り替え自体が存在しなかった——つまり現状、モバイルユーザーはComparisonというReading Stateにほぼ到達できない。ここが実質的な白紙であり、最も丁寧に設計すべき部分である。

### 5.2 基本方向：Stacked Reading

有力な方向として **Vertical Stacking**（Translation A の上に Translation B を積む）を採用する。

```text
┌───────────────────────────┐
│ ‹ ローマ 1章 ▾   比較 ···  │  Contextual header（Bible Location + Reading State表示）
├───────────────────────────┤
│ 口語訳（1955）              │  Translation A label（ui-label, ink-secondary）
│ ── ── ── ── ── ── ── ──    │
│ 1  キリスト・イエスの僕、…  │  verse-ja-comparison
│ 2  この福音は、神が、…     │
│ 3  御子に関するものである。…│
├─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─┤  space-7 の間隔 + 軽い区切り線（border-hairline）
│ 新改訳2017                  │  Translation B label
│ ── ── ── ── ── ── ── ──    │
│ 1  キリスト・イエスのしもべ、…│
│ 2  ……                      │
│ 3  ……                      │
└───────────────────────────┘
```

理由：
- 横方向の分割（左右2ペイン）は、日本語・ギリシャ語ともに1行の文字数が確保できず、どちらの翻訳も「読める密度」を割ってしまう。縦積みなら、各翻訳が画面幅いっぱいの、単独読書時とほぼ同じ組版幅を維持できる（`verse-ja-comparison` は `verse-ja` より1段階小さいだけで、行幅を犠牲にしない）。
- 縦積みは「両方を続けて読む」という体験に自然に一致する——1節ずつ視線を往復させる差分読みではなく、Aをひとかたまり読んでからBをひとかたまり読む、という読書行動に沿う。

以下、A/Bそれぞれの節番号表示・対応節への移動・現在位置の保持・スクロール中の翻訳識別の4点を具体化する。共通の前提として、**常時スクロール同期は行わず、Swipe切替も既定にしない**——読む流れは「Aを上から下へ読み進め、そのままBへ読み進める」という、ひとつづきのスクロールのままにし、AとBを行き来する負担だけを、必要なときに使える最小限の手段で減らす。

### 5.3 スクロール構造：単一の連続スクロール

Translation AブロックとBブロックは、別々のスクロール領域（2つのスクロールビュー）に分けない。画面全体がひとつの縦スクロールで、その中にA→Bの順にブロックが並ぶ——長い1つのページを読んでいるのと同じ操作感にする。これにより：

- 「今どちらのペインをスクロールしているか」という余計な判断が発生しない（片方が独立スクロールだと、指を置く位置によって動く対象が変わり、誤操作の原因になる）。
- Comparison Synchronization（`03`§3）で述べた「追従」——片方をスクロールするともう片方も動く——という常時連動の仕組みが不要になる。連動させる対象がそもそも1つのスクロールしかないため、「ズレる／追従が過敏で酔う」という失敗モードが構造的に起こらない。

Bible Locationの表示（ヘッダー）は、画面内で最も上に見えている節を基準に更新する。AとBのどちらの節かは、後述§5.5のSticky Labelと合わせて判断する。

### 5.4 A/Bそれぞれの節番号表示

AブロックとBブロックは、それぞれ独立した節番号を持つ（1節から自ブロック内で振り直す。全体を通し番号にはしない）。番号は`Verse`コンポーネントと同じ`ui-caption` / `ink-tertiary`で、本文の左に`space-2`空けて置く——これはSingle Readingと同じ見た目で、Comparisonだからといって特別な採番方式（例：A1/B1のような接頭辞、色分けされた番号）を持ち込まない。

理由：番号の見た目を翻訳ごとに変えると、それ自体が「差分を意識させる装飾」になり、`03`§4のDiff Highlighting回避の原則に反する。どちらの翻訳の節番号かは、番号の隣ではなく、後述のSticky Label（§5.5）と、ブロック先頭の`Translation Label`（口語訳（1955）／新改訳2017）で判断できれば十分であり、番号自体を加工する必要はない。

### 5.5 スクロール中の翻訳識別：Sticky Translation Label

Aブロックの節番号だけを見ても「1」「2」…としか分からず、Bブロックの節番号と区別がつかない。ブロック先頭の`Translation Label`（口語訳（1955）等）はスクロールすると画面外へ出てしまうため、長い章では「今読んでいるのはどちらの翻訳か」を見失う可能性がある。

これに対して、追加のスクロール連動処理やヘッダーの常時表示ではなく、**各ブロックの`Translation Label`をCSSの`position: sticky`にする**という、最小限の手段を提案する。

- 画面をAブロックの範囲でスクロールしている間、Aの`Translation Label`（「口語訳（1955）」）がヘッダー直下に張り付いたまま残る。
- スクロールがBブロックの範囲に入ると、Bの`Translation Label`（「新改訳2017」）が下から上がってきてAのラベルを押し出し、以後はBのラベルが張り付く。
- ラベル自体は`ui-label` / `ink-secondary`のままで、Sticky化のために背景や太さを強調しない（`surface-canvas`と同系色の薄い背景のみを敷き、下の本文が透けて重ならない程度にする）。

この方法を選ぶ理由：ブラウザ標準の挙動だけで実現でき、スクロール位置を監視して何かを常時計算・追従させる仕組みを新たに作らずに済む——つまり「常時スクロール同期」を増やさずに「今どちらを読んでいるか分からなくなる」問題だけを解消できる。iOSの連絡先一覧などで使われる、見出しが切り替わる感覚に近い、既に広く馴染みのあるパターンでもある。

### 5.6 対応する節への移動：明示的な一回限りのジャンプ

「同じ箇所を見比べる」ときの負担は、多くの場合「今Aで読んでいる節が、Bのどこにあるか探す」というスクロール操作そのものである。これを、常時同期ではなく、**ユーザーが求めたときにだけ働く、一回限りのジャンプ**で軽減する。

- 節番号（`ui-caption`の数字部分）をタップすると、もう一方のブロックの同じ節番号へスムーズスクロールする（`scrollIntoView`相当、値は`10-motion.md`を参照）。
- 到着後、その節の背景を`accent-greek-100`で一瞬敷き、0.6秒でフェードアウトさせる——`07-representative-screens.md` #9（Research → Return）で定義した「戻った場所を示す」ハイライトと同じ視覚言語を流用し、システム内で一貫させる。
- この操作は往復可能——Bの節番号をタップすればAの同じ節へ戻れる。
- 本文（節番号ではなくテキスト部分）のタップは、Single Readingと同じくResearch起点として扱う。Comparison中は「番号＝対応節へ移動」「本文＝調べる」という役割分担にし、Verseコンポーネントの既定（番号を含む節全体がResearch起点）から意図的に外れる——`06-component-architecture.md`のVerse仕様にこの例外を明記する。
- ジャンプが常設の矢印やリンクとして画面に出っぱなしにはしない。節番号自体が押せることの手掛かりは、初回利用時のワンタイムなヒント（ツールチップ等）で示す想定とし、常時デコレーション（下線・アイコン常設）は付けない——Diff Viewer的な見た目を避けるため。

### 5.7 現在位置の保持

Comparisonは単一の連続スクロールのため（§5.3）、保持すべき位置情報は「画面上端に最も近い節が、AかBのどちらの、何節か」という1つの値で足りる（例：`{ side: "B", verse: 5 }`）。これを`04-research-and-state-transitions.md`のReading Positionスナップショットに含め、次のいずれの場合も同じ値から復元する：

- Researchへ入って戻ってきたとき（`04`§3 Research Return）
- Comparisonを離れてSingleに切り替え、再度Comparisonに戻したとき
- アプリを再開したとき（履歴からの復元）

章送り時は、`04`§4の原則どおりA・Bとも新しい章の1節目から開始し、位置スナップショットもリセットする——章をまたいでの位置保持は行わない。

### 5.8 常時スクロール同期・Swipe切替を既定にしない理由

SegmentedタブやSwipeでAとBを切り替える方式（一度に片方しか見えない）、あるいは片方のスクロールにもう片方を常時追従させる方式のいずれも、既定には採用しない。

- Swipe/Toggleは、結局は単独読書を往復しているだけで、「同じ箇所を両方で読める」というComparisonの目的（`03`§1）——両方が同時に視界にある——を満たさない。
- 常時スクロール同期は、翻訳ごとの文章量・改行の違いにより、意図しない位置に連動してしまう失敗が起きやすく、かつ実装・検証コストの高いわりに、§5.3の「単一連続スクロール」で同じ目的（迷わないこと）がより単純に達成できる。

Swipe/Toggleを完全に禁じるわけではなく、Comparisonの**補助**（長い章で、Aを読み終えてBの対応箇所へ一気に移りたいときの§5.6ジャンプ機能）としてのみ使う。既定の表示・操作方式はあくまでStacked Reading＋一回限りのジャンプである。

### 5.9 Mobile ComparisonのSetup導線

Comparison Setup（Translation B選択）は、Contextual headerの「比較」ラベルタップから開くボトムシートで行う。デスクトップの「読み方を選ぶ」パネルと同じ情報構造（Reading State → Translation A/B → View Mode）を、1画面1判断のステップに分解して提示する（`06` ReadingModePickerコンポーネント参照）——モバイルでは同時に多くの選択肢を見せない。

### 5.10 要確認事項（既存実装への依存——実現済みと仮定しない）

以下は、既存のBible Engine・データ・履歴機構に依存する前提であり、本Phaseでは実機・データの直接確認ができていない。実装着手前に個別に検証すること。

- **節番号の翻訳間対応が1:1かどうか。** §5.6の「同じ節番号へジャンプ」は、AとBの節番号が原則1対1で対応することを前提にしている。結合節・分割節・欠番節（写本上の理由で一部節が存在しない翻訳がある等）が存在する場合、単純な番号一致では対応が取れない。既存データに翻訳間の節対応表（versification mapping）が存在するか、存在しない場合はどの範囲で1:1が崩れるかを、対象翻訳ごとに確認する必要がある。対応が取れない節では、ジャンプ操作を無効化するか、最も近い節へフォールバックし、その旨を`ink-tertiary`の小さな注記で示す設計にすべきだが、具体化はこの確認の後に行う。
- **Translation Bの本文をアプリ内データとして保持しているか。** 実機調査で確認できたのは、口語訳（1955）本文と、外部サイトへ離脱する形の「外部の翻訳で比較」（新改訳2017・新共同訳）のみである。§5全体はTranslation Bをアプリ内で同一画面に表示できることを前提にしているが、これが既存データ・ライセンスの範囲で可能かは、`09-implementation-priorities.md` Phase 4の権利関係確認に懸かっており、未確認である。
- **Reading Position履歴の保存粒度。** 既存実装の「最近読んだ箇所」がBook/Chapter/Verseレベルの粒度なのか、§5.7で必要な「AかBか＋節番号」まで保存できる構造なのかは未確認。現状の粒度が粗い場合、Comparison用のスナップショットは新規のデータ項目として追加する必要がある。
- **節番号タップの操作が既存のジェスチャーと衝突しないか。** ハイライト機能・語タップ（Research起点）・既存の「前の語の読解に戻る」導線など、実機で確認済みの既存タップ／長押し挙動との衝突がないか、§5.6の「番号タップ＝ジャンプ」を実装する前に、既存実装のイベントハンドリングを確認する必要がある。
- **Sticky Labelの表示範囲での既存レイアウトとの干渉。** `position: sticky`はヘッダー（Contextual header）の高さやz-indexに依存する。既存のヘッダー実装がstickyポジショニングと衝突しないか（例:ヘッダー自体が固定要素で、Sticky Labelとの重なりが発生しないか）は、実機のCSS構造を確認していないため未確認。

## 6. Avoid（再掲・適用）

- Excessive diff highlighting
- Multi-translation grids（3列以上のグリッド表示）
- Complex comparison controls
- Data table化

これらはComparison UXおよびMobile Comparison双方に適用される絶対原則である。
