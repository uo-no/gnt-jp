## 0. 前提整理

### 判断軸（CLAUDE.md First Principle に基づく）

> **Reading Japanese は翻訳ではない。ギリシャ語の構造を「読むための」日本語表示である。**

訳語変更の基準:

1. 現在の `ja` がギリシャ語の構造的意味を読者に伝えていないか
2. 誤解を招く表示か（意味の上書き）
3. 変更後の `ja` も L-0 境界を守るか（referent 解決・文脈解釈をしない）

### 変更候補の分類方針

- **変更推奨**: 現在の `ja` が意味クラスターと正反対の語義を持つ
- **変更容認**: 現在の `ja` が意味を伝えないが積極的な誤解は生じない
- **維持推奨**: 現在の `ja` で意味が伝わる、またはより良い代替がない
- **HOLD**: 語根・Strong 番号・lemma の問題を先に解決する必要がある

## 1. G863 ἀφίημι — 現在: `赦す`

### 1.1 推奨方針: **オプション E（変更候補個別修正）**

**理由**:

- Cluster A（47件）は `赦す` で正確。変更不要。
- Cluster B（63件）・C（33件）合計 96件は `赦す` が意味的に不適切。
  - 「羊を赦す」「使徒たちが逃げて赦す」「子を来させるよう赦す」は明確に意味錯誤。
- Cluster B・C に共通する単一語はないため、クラスター別に異なる `ja` を使う必要がある。

**推奨 `ja` 割当て**:

| クラスター | 推奨 `ja` | 補足 |
|-----------|----------|------|
| A (47件) | `赦す` | 変更なし |
| B — 去る/離れる (主用) | `去る` | MAT 4:20 等 |
| B — 捨てる/見捨てる | `捨てる` | JHN 10:12、MAT 26:56 等 |
| B — 疎かにする | `疎かにする` | MAT 23:23 |
| B — 残す/置き去り | `残す` | MRK 12:19、LUK 17:35 |
| B — 霊を放つ（死） | `放つ` | MAT 27:50、MRK 15:37 |
| C — 許可する/させる (主用) | `許す` | MAT 19:14 等 |
| C — 黙認する/容認する | `黙認する` | REV 2:20 |
| C — 離縁する | `去らせる` | 1CO 7:11–13 |

**変更規模**: 最大 96件（bible_data `token.japanese` 変更）

**注意**: Cluster B と C の境界トークン（約 10件）は個別確認を推奨する。特に `ἄφες` (V-2AAM-2S) は文脈によって B or C に分かれる。

### 1.2 形態コードによる機械分類の利用可能性

- 受動形 (V-xPI/xPS): Cluster A の確率が高い → 自動で `赦す` 維持候補
- 能動分詞 V-2AAP/AAP: Cluster B の確率が高い → 要確認
- 能動命令形 V-2AAM/AAM: Cluster C の確率が高い → 要確認

受動 = A の自動判定は高精度だが、LUK 17:35 のような例外（受動 = B）が存在するため、完全自動適用前に全受動形（約 40件）の確認を推奨する。

### 1.3 優先度: **高**

影響 96件。意味錯誤の程度が大きい（「赦す」↔「去る/許可」は語義的に無関係）。

## 2. G1210 δέω — 現在: `縛る`

### 2.1 問題の二層構造

**第1層（主問題）: δεῖ 形 85件の `ja` が `縛る`**

現状: G1210 の 85/138 件 (61.6%) が δεῖ（〜しなければならない）の活用形だが `ja = 縛る`。  
`縛る` は δεῖ の意味（義務・必要）を読者に全く伝えない。

**第2層（別問題）: δέομαι 形 10件の Strong アサインメント**

現状: G1210 に登録された 10件が実際は δέομαι (G1189 = 求める/祈る) の語根。  
`ja = 縛る` は意味的に完全に誤っているが、問題の根はデータ設計にある。

### 2.2 第1層の推奨方針: **オプション D（dei-necessity 個別修正）**

δεῖ 形 85件の `token.japanese` を `〜しなければならない` に変更する。

**推奨理由**:

- δεῖ は形態コード (V-PAI-3S / V-PAN / V-PAS-3S / V-PAP-NSN/APN) で高精度に機械判別できる。
- Strong 番号は変更しない（bible_data の設計方針を尊重）。
- `〜しなければならない` は δεῖ の構造的意味を直接示し、L-0 境界を守る。

**留意**: 「推定 ~97件」という Phase 4g 見積もりは再評価された。全数は **85件**（deom-hold 10件と未分類が含まれていた）。

**変更対象の特定方法**:

```
G1210 全件のうち:
  morph IN (V-PAI-3S, V-PAN, V-PAS-3S, V-PAP-NSN, V-PAP-APN) → dei-necessity 候補
  text MATCHES /^[Δδ]εῖ$|^δεῖν$|^δέῃ$|^δέον$|^δέοντα$/ → dei-necessity 確定
```

**変更規模**: 85件

### 2.3 第2層の推奨方針（deom-hold 10件）

#### 選択肢 2A: トークン個別 `japanese` 修正のみ

10件の `token.japanese` を δέομαι の意味に即した語（例: `求める`・`祈る`）に変更する。  
Strong 番号は G1210 のまま維持。  
最小変更。既存の Strong-lexicon マッピングへの影響なし。

#### 選択肢 2B: Strong 番号を G1189 へ変更

bible_data の strong フィールドを G1210 → G1189 に変更する（10件）。  
G1163 (/G1189) への関連処理（lexicon lookup 等）が既存で存在する場合は整合性が増す。  
変更規模は小さい（10件）が、bible_data の strong フィールド変更は bible_data 設計に関わる判断。

**推奨**: 選択肢 2A（トークン修正のみ）を先行させ、Strong 番号変更は別途検討。  
理由: Strong 番号変更は bible_data の設計判断を伴い、現在の Phase 4h の調査スコープ外。

### 2.4 優先度: **高**（dei-necessity 85件）/ **中**（deom-hold 10件）

dei-necessity は件数・意味錯誤の大きさともに深刻。`縛る` と `〜しなければならない` の意味的乖離は G863 と同等以上。

## 3. G2919 κρίνω — 現在: `裁く`

### 3.1 推奨方針: **オプション B（decide 9件の個別修正）**

106/115 件 (92.2%) は `裁く` で正確。変更候補 decide 9件のみを修正する。

**推奨 `ja`**: `決める`（または `定める`）

- `決める` は κρίνω = "to decide/determine" の構造的意味を伝える。
- L-0 境界を守る（referent を推論しない）。
- `裁く` との語義的距離が明確で、読者が文脈を正確に把握できる。

**変更対象 9件**:

| ref | 原文 | morph | 文脈 |
|-----|------|-------|------|
| ACT 3:13!27 | κρίναντος | V-AAP-GSM | ピラトが釈放を決定 |
| ACT 20:16!1 | κεκρίκει | V-LAI-3S | パウロがエフェソ素通りを決定 |
| ACT 25:25!15 | ἔκρινα | V-AAI-1S | フェストがカエサル上訴を認定 |
| ACT 27:1!3 | ἐκρίθη | V-API-3S | 航海の決定 |
| ROM 14:13!7 | κρίνατε | V-AAM-2P | 「つまずきを置かないと決める」|
| 1CO 2:2!3 | ἔκρινά | V-AAI-1S | パウロの宣教方針 |
| 1CO 7:37!21 | κέκρικεν | V-RAI-3S | 結婚しないと決めた |
| 2CO 2:1!1 | ἔκρινα | V-AAI-1S | 悲しみをもって行かないと決めた |
| TIT 3:12!16 | κέκρικα | V-RAI-1S | アルテマスを送ることにした |

> **ACT 3:13 境界例注記**: ピラトの「釈放を決定」は judicial context でもあり得る。変更適用前に確認を推奨。他 8件は高信頼度。

**変更規模**: 最大 9件

### 3.2 優先度: **低**

影響件数が最小（9件）。意味的不一致は中程度（`裁く`「判断する」は意味的に遠くはない）。G863・G1210 対応後に実施推奨。

## 5. 変更実施時の制約

### 5.1 L-0 境界の維持

変更後の `ja` も以下を守ること:

- referent を解決しない（「弟子たちが（イエスを）捨てて逃げた」→ `去る` で十分）
- 文脈訳にしない（「ピラトが釈放を決めた」→ `決める` の構造表示に留める）
- 感情・ニュアンスを加えない

### 5.2 変更後の回帰確認

- G863 変更: `赦す` を使う UI 表示パス（StudyPanel 等）で表示確認が必要
- G1210 変更: 形態コード判別ロジックを使う場合、unit test を追加推奨
- `reading-engine.js` の Phase 4 lexicon 処理が `token.japanese` を直接使うか lexicon テーブル経由かを事前に確認する

### 5.3 bible_data 変更プロトコル

bible_data の `token.japanese` 変更は以下の手順を推奨:

1. 変更対象リストを事前に JSON で出力し、ユーザー確認を経る
2. バックアップを取得する
3. diff 形式で確認後に適用する
4. 変更後に影響範囲のスクリーンショット取得
