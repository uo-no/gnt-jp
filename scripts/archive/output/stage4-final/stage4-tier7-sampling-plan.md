# Stage 4 監査方式確定：Strong 単位・Token 単位・サンプリング設計

生成日: 2026-10-31  
根拠データ: stage4-strong-order.json / stage4-group-assignment.json

---

## 0. 設計の前提

### A：Strong 単位の基本語彙確認

各 Strong について次を確認する。

- 基本語義と品詞
- 現在の japanese ラベルの妥当性
- 語義の過度な限定・拡張がないか
- JA1955 の訳語との整合性（代表箇所）
- 文脈依存の意味を基本ラベルに誤って固定していないか

**原則: 全 Strong を対象とし、サンプリングで省略しない。**

Tier・グループを問わず、Strong 単位の確認（A）は全件実施する。

### B：Token 単位の文脈確認

全 tokens を確認できない Strong については層別サンプリングを設計する。

| 設計上の明示事項 |
|----------------|
| 1. Strong ごとの tokens 数 |
| 2. 抽出時の層別条件（品詞・形態・用法・書巻） |
| 3. 各層の母集団数とサンプル数 |
| 4. サンプル数の決定根拠 |
| 5. 乱数シードを含む抽出方法 |
| 6. 複数用法がサンプルから漏れない仕組み |
| 7. 問題発見時の拡大監査条件 |
| 8. 全件確認に切り替える条件 |

### サンプル PASS の意味

サンプルで問題が発見されなかったことは、未確認 tokens が正しいことを保証しない。  
「サンプル PASS」は「当該 Strong の該当サンプル期間に重大な問題は確認されなかった」を意味する。

信頼区間を示す場合、それは母集団全体の誤り率の確定値ではなく推計値である。

### 1.2 Strong 単位確認（A）

全 4,195 Strongs を対象とする。Strong-level では:
- 1件〜数件の代表的な bible_data token を読む（n が小さい場合は全件が代表）
- lemma・語義・ラベルを照合
- PASS / NOTE / AMBIGUOUS / CONFIRMED_ERROR を判定

### 1.3 Token 単位確認（B）— Tier 別設計

#### Tier 1（n≥200、20 Strongs、8,724 tokens）

**目的**: 高頻度動詞・形容詞の多様な用法を網羅的にサンプリング  
**層別次元**: 書巻区分（4区）× 形態（tense × mood）  
**サンプル数/Strong**: 15〜20 tokens（目標 tokens = n × 4〜5%）  
**最小保証**: 各書巻区分から最低 2 tokens

書巻区分:
- 区 I: 共観（MAT/MRK/LUK）
- 区 II: ヨハネ文書（JHN/1JN/2JN/3JN/REV）
- 区 III: 使徒（ACT）
- 区 IV: 書簡（ROM〜JUD）

乱数シード: `Strong 番号の数値部分 % 10000`（再現可能）  
拡大条件: サンプル内で NOTE/AMBIGUOUS > 3件 → 該当層を全件確認  
全件切替条件: CONFIRMED_ERROR または AMBIGUOUS > 30% → 全件確認

#### Tier 2（n=100-199、36 Strongs、4,966 tokens）

**サンプル数/Strong**: 10〜15 tokens（n × 7〜10%）  
**層別**: 書巻区分（4区）から各最低 2 tokens + morph 分布を反映  
乱数シード: 同上  
拡大条件: NOTE/AMBIGUOUS ≥ 2件 → 2× 拡大  
全件切替条件: 同上

#### Tier 3（n=50-99、79 Strongs、5,548 tokens）

**サンプル数/Strong**: 8〜12 tokens（n × 10〜15%）  
**層別**: 書巻区分（4区）× 主要 morph（可能な範囲で）  
拡大条件: NOTE/AMBIGUOUS ≥ 2件 → 全件確認（≤99 tokens で管理可能）  
全件切替条件: n≤60 の場合は全件確認を推奨（負担が小さい）

#### Tier 4（n=20-49、212 Strongs、6,534 tokens）

**サンプル数/Strong**: 8〜12 tokens（n × 25〜40%）  
**層別**: 書巻区分（2区：共観+ヨハネ vs 使徒行伝+書簡）  
拡大条件: NOTE/AMBIGUOUS ≥ 2件 → 全件確認（≤49 tokens は管理可能）

#### Tier 5（n=10-19、347 Strongs、4,585 tokens）

**サンプル数/Strong**: 6〜8 tokens（n × 40〜60%）  
**層別**: 書巻区分（2区）から各最低 2 tokens  
拡大条件: NOTE/AMBIGUOUS ≥ 1件 → 全件確認（≤19 tokens）

#### Tier 6（n=5-9、591 Strongs、3,895 tokens）

**方式**: 全件確認  
**根拠**: n が 5〜9 tokens と少なく、サンプリングより全件確認が効率的かつ確実  
**実施単位**: Strong ごとに全 tokens を連続確認

#### Tier 7（n=1-4、2,910 Strongs、5,058 tokens）

**方式**: 全件確認（サンプリング不要）  
**根拠**: n が 1〜4 と極小であり、すべての tokens を確認することが実質的に Strong-level 確認と同等

| n | Strongs | Tokens | 確認コスト |
|---|---------|--------|-----------|
| 1 | 1,624 | 1,624 | 1件/Strong |
| 2 | 659 | 1,318 | 2件/Strong |
| 3 | 392 | 1,176 | 3件/Strong |
| 4 | 235 | 940 | 4件/Strong |
| 合計 | 2,910 | 5,058 | |

**Tier 7 の監査方式**:

1. **バッチ処理による Strong 単位確認**
   - 語彙的に透明な lemma（固有名詞を除く名詞・形容詞の大多数）は Strong 単位で一括確認
   - ラベルが明確に適切なら PASS として記録、個別 token 確認を省略できる
   - ラベルが疑わしい場合のみ全 tokens（最大 4 件）を確認

2. **hapax legomena（n=1、1,624 Strongs）の扱い**
   - n=1 は「その 1 token = そのラベルの唯一の根拠」
   - Strong-level 確認時に 1 token を必ず確認済み → 追加 token 確認なし
   - JA1955 との対応確認は 1 件の文脈から判断

3. **同一用法グループ内の効率化**（PERMITTED）
   - 同一品詞・同一意味領域の Strongs を連続して処理することで判断効率を高める
   - ただし「同一グループの前の Strong が PASS だったから後続も PASS」という推論はしない
   - 各 Strong の判断は独立

4. **Tier 7 の AMBIGUOUS 判定方針**
   - n=1〜2 で JA1955 との対応が文脈から判断できない場合 → AMBIGUOUS
   - AMBIGUOUS は Stage 5（既存 55 件との再検討フェーズ）への送り判断と同様に扱う
   - Tier 7 の AMBIGUOUS を Stage 4 内で解決しようとしない

## 11. 拡大監査・全件切替条件

### 全件切替の一般条件

次のいずれかを満たす場合、サンプリングから全件確認に切り替える:

1. CONFIRMED_ERROR が 1件でも発見された
2. サンプル内の AMBIGUOUS > 25%
3. 連続する書巻区分で同一パターンの問題が検出された
4. n ≤ 20 かつ NOTE ≥ 1件

### AMBIGUOUS の扱い

- Stage 4 内で解決しようとしない
- AMBIGUOUS として記録し、Stage 5（既存55件の再検討）と同様のキューに追加
- AMBIGUOUS はサンプル PASS に算入しない（保留として扱う）

### サンプル FAIL の定義

サンプル内で次のいずれかが検出された場合を FAIL とし、拡大監査をトリガーする:

- CONFIRMED_ERROR（語義ラベルが明確に誤り）
- NOTE × 2件以上（語義ラベルが疑わしい）
- 同一パターンの問題が書巻をまたいで出現

## 付記：Tier 7 に対する特別注記

Tier 7（n=1-4、2,910 Strongs）は「サンプリングの設計対象ではない」。

サンプリングとは「全 tokens から代表的なサブセットを選ぶ」設計であり、n=1〜4 では全件確認が実質的にサンプルと同義である。

Tier 7 の監査工数は:
- n=1: 1,624 Strongs × 1件 = 1,624 token 確認
- n=2-4: 1,286 Strongs × 2-4件 = ~3,434 token 確認

合計約 5,058 tokens。しかし各 token は 1〜2行の bible_data 参照で確認できる。

**Tier 7 の実際の課題は件数ではなく件数の多さによる認知負荷**。そのため:
- 意味領域別（動詞 / 名詞 / 形容詞 / 副詞）にバッチ処理
- ラベルが明確な Strongs を先に処理し、不明なものを後回し
- AMBIGUOUS は積み残しリストへ追加して一括処理
