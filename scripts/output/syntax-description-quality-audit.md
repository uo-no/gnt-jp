## 4. 全体に適用する改稿基準

1. **用語は消さず、意味を説明する**: 「述語属格」などの型名は保持し、説明文ではその用法が文中で何をしているかを平易に示す。
2. **専門語を初出で噛み砕く**: 「ヘッド名詞」は原則として「中心となる名詞」などに言い換える。必要なら括弧で専門語を補う。
3. **意味役割と形の条件を分ける**: 「何を表す用法か」と「どの形・構文に現れるか」を混同しない。
4. **分析レベルを区別する**: 形態（時制・法・態）、句内機能、節機能、談話機能を同じ説明に混在させない。
5. **例は定義の代わりにしない**: 例は説明を補助するものとして扱い、解釈に議論がある聖句を唯一の正解例として提示しない。
6. **確度を過大にしない**: 文脈依存・議論のある用法は「〜と読めることがある」「文脈により判断」と明示する。
7. **内部実装の説明を読者向け本文に混ぜない**: 他レイヤーが担う、シグナル名、判定ルールなどは必要に応じて監査メモへ分離する。
8. **原典根拠を記録する**: Wallaceの節・ページと、可能な限り新約聖書の実例を照合する。未確認の根拠を「確認済み」と記載しない。

### 第2回レビューでの横断的な注意

- **形と意味を同一視しない**: 現在形＝進行、アオリスト命令＝一回限り、冠詞＝既知・特定、といった読みを説明文だけで固定しない。文脈・語彙・構文が解釈に関わる場合は明記する。
- **検出ヒントと読者向け定義を分ける**: `hint_ja` は「ἵναがある」「前方に発話動詞がない」などの検出上の手掛かりを含む。これをそのまま `description_ja` の定義に移さない。
- **重複する分析レイヤーを明示する**: `verb.purpose_clause` は接続法の構文上の用法、`clause.purpose_hina` は節全体の目的機能を扱う設計意図と考えられるが、この分担が分類体系・実際の解析と一致しているかは別途確認する。
- **自動判定の限界を表示説明に反映する**: `example_verse` や `hint_ja` が示す例・シグナルは、型の自動検出を支援するもので、文法的解釈を単独で確定する証拠とは限らない。
