# StudyPanel 情報方針：本文の事実・分析候補・判断基準

作成: 2026-10-23  
状態: 設計方針案（UI・解析コードは未変更）

## 1. 目的

新約聖書のすべての箇所に、個別に完成された意味論的解説を作ることを必須要件にしない。全箇所で品質を保証しやすい「本文から確認できる事実」「文法・統語上の可能性」「候補を区別する判断基準」を中核にする。

これは解釈の放棄ではない。本文・形態・構造から確かめられる情報と、文脈を踏まえた解釈的推論を区別し、根拠の弱い断定を避けるための方針である。

## 2. 情報を3種類に分ける

### A. 本文から確認できる情報

例:
- 表層形、見出し語、品詞、形態情報
- 語順、接続表現、前置詞句
- データから再現可能な参照関係
- 明示的な節・句の構造（データがその構造を保持し、根拠を追跡できる場合）

要件:
- 原文・データに照合できること
- 派生した解釈を事実として表示しないこと
- 参照先を表示する場合、参照先の単一トークンを人物名や句全体へ勝手に拡張しないこと

### B. 文法・統語上の可能性

例:
- 属格の機能候補
- 分詞・不定詞の統語機能候補
- 語順による話題化・強調等の可能性
- 代名詞・分詞の参照先候補

要件:
- 候補は形態・構造・文法的根拠によって成立するものに限る
- 候補名だけを並べず、候補間の実質的な違いを説明する
- スコアや順位は解析器の出力であり、解釈の正しさそのものではないと扱う
- 候補が一つに絞れないことを、システムの失敗とみなさない

### C. 判断基準・注目すべき文脈

候補を区別するため、読者が何を見るべきかを示す。

例:
- どの語・句が対象表現と統語的に結びつくか
- 直前・直後の節がどの関係を示しているか
- 同じ語・構文の用例と、今回の文脈の共通点・相違点
- 各候補を支持／弱化する証拠
- 何が分かっていて、何がデータだけでは決められないか

「文脈を見てください」という抽象的な注意だけでは不十分。可能な限り、確認対象を具体的に示す。

## 3. 断定の強さを根拠に合わせる

| 根拠の状態 | 表示方針 |
|---|---|
| 原文・形態から確認可能 | 事実として示す |
| 構造上強く支持される | 根拠を添えて有力な分析として示す |
| 複数の文法分析が成立 | 候補と区別基準を示す |
| 文脈・語用論・意味論の判断を含む | 推論であることを明確にし、根拠と留保を示す |
| 現在のデータでは判定できない | 無理に埋めず、不確定とする |

候補の順位・スコアだけで意味を確定しない。統語的な判定と、文脈上の意味解釈を混同しない。

## 4. StudyPanelの情報階層

### Layer 1 — 読む
- 本文
- 語順表示
- 読書を止めないための最小限の語義・導線

### Layer 2 — 理解する
- 短い読書メモ（利用できる根拠がある場合）
- 文中での役割
- 主要候補と代替候補の実質的な違い
- 判断基準・注目すべき文脈
- 参照先や句・節との関係を理解するための根拠

Layer 2の説明はすべてのトークンに必須ではない。根拠がない箇所に定型文を無理に生成しない。

### Layer 3 — さらに調べる
- 形態情報の詳細
- 見出し語、Strong等の識別情報
- 辞書全文（Abbott-Smithを含む既存資産を保持）
- 用例・使用傾向
- 関連する文法資料・研究リンク
- 必要な場合の詳細な分析根拠

Layer 3は研究情報の保管場所であり、Layer 2の説明を長く重複して掲載する場所ではない。辞書全文・用例・合成的な語義説明は、短い読書メモを優先するために削除しない。

## 5. 既存情報の扱い

### 残す
- 原文・形態と照合できる事実
- 出典・根拠を追跡できる文法情報
- 辞書全文、用例、研究リンクなどの参照資産
- 本文理解に直接寄与し、根拠を説明できる読書メモ

### 再構成する
- 候補名だけを列挙する表示
- 文法的な根拠と意味解釈が混ざっている説明
- 汎用説明が、すべての箇所に個別の結論として表示される仕組み
- Layer 2とLayer 3に同じ情報を重複表示する箇所
- PCとモバイルで情報の役割・優先順位が不必要に異なる箇所

### 断定を弱める／表示しない
- 形態だけから意味・談話機能を確定している説明
- スコアや順位を解釈の確実性と誤認させる表示
- 参照先データが表現できる範囲を超えて人物名・句全体などを推定する表示
- 根拠を確認できない自動生成説明
- 読者が検証できない「この語は必ず〜を意味する」型の説明

「断定を弱める」はデータを一律削除することを意味しない。根拠が不足する場合は、候補・留保・非表示のいずれが適切かを個別に判断する。

## 6. 監査手順

1. 現行のLayer仕様と実装を照合し、項目ごとに「実装済み／未実装／重複／表示不具合／内容要検証」を記録する。
2. データ生成元、参照関係、UI表示経路を分けて追跡する。
3. 代表例で情報分類を検証する。最初のケースはエペソ1:10の ἀνακεφαλαιώσασθαι と、エペソ1:9–10の Χριστῷ。
4. Wallaceを新約ギリシャ語の文法・統語の主要な参照枠として照合し、本文・近接文脈・実例を確認する。文法書の分類をそのまま意味論的結論に置き換えない。
5. 同じ生成規則が適用される全新約データに範囲を広げ、例外・高リスクの型を抽出する。
6. 内容の問題と表示UIの問題を分離してから、修正を提案・実装する。
7. 修正後は影響範囲に応じた全体テスト、PC／モバイル確認、差分監査、CIを行い、結果を記録する。

## 7. 初期ケース：エペソ1:10

対象語: ἀνακεφαλαιώσασθαι

監査で分けて確認すること:
- 形態情報が実際の語形と一致するか
- 不定詞が文中でどの表現に依存するか
- 「命令的不定詞」などのラベルが当該箇所に適用される根拠があるか
- subjref等の参照データがどのトークンを指すか
- 表示文がデータの意味を過度に拡張していないか
- 辞書の語義と、当該文脈での解釈が区別されているか

この監査は設計・検証の出発点であり、単一のスクリーンショットだけから新約全体の誤り率を推定しない。

## 8. リリース判定基準

- 形態情報と参照データが元データと一致する。
- 候補は文法的に成立し、説明が候補間の違いを表している。
- 判断基準は対象候補の区別に実際に役立つ。
- 文脈上の観察と解釈的推論が区別されている。
- 根拠が不足する箇所で、システムが断定を捏造しない。
- 既存の辞書・用例・研究資料が不用意に失われていない。
- 新約全体の回帰テストとPC／モバイルの表示確認が完了している。
- 変更理由、対象ファイル、検証結果、コミット、CI状態を記録している。

## 10. 初回データ追跡結果（2026-10-23）

現行 `main` の `public/bible_data/nt/EPH/1.json` と `public/assets/data/syntax-registry.json` を読み取り専用で照合した。

### ἀνακεφαλαιώσασθαι（EPH 1:10!7）

- トークンID `103809`、形態 `V-ADN`。データ上はアオリスト・中動態・不定詞。
- `subjref` は `n49001003003` を指し、解決先は EPH 1:3!3 の `θεὸς`（japanese:「神」）。
- `frame` は `A0:n49001003003 A1:n49001010009`。subjrefと同じ神のトークンをA0として記録している。
- したがって、表示文「この語の主語は『神』です」は参照データの転写として生成された可能性が高く、直ちに誤表示とは判定できない。ただし、これはデータ上の意味上の主語参照を表す説明であり、不定詞に定形動詞の主語と同じ文法形式があるという意味ではない。表示文言は「この不定詞の意味上の主語として、データは『神』を指しています」等、参照の性質を明示する選択肢を検討する。
- `syntax-registry.json` の `infinitive.imperatival` は、ROM 12:15を例とし、「定形動詞のない節で命令として機能する不定詞」と定義される。EPH 1:10への適用はこの説明だけでは支持されない。今回のスクリーンショットの「命令的不定詞」表示は、汎用説明が誤って当該語へ結びついた可能性があるため、解析出力・候補選択・説明文表示経路の追跡を要する。現段階で原因箇所や全体件数は未確定。
- 次の確認対象は、EPH 1:10!7の解析器出力に `infinitive.imperatival` が含まれるか、別候補の説明を誤って表示していないか、候補と説明文のデータ結合が正しいか、の3点。

### Χριστῷについての確認範囲

- スクリーンショットの見出し語 `Χριστός`・Strong G5547・与格単数男性は、該当する語形の基本情報として確認対象にできる。
- 「左方転位（懸垂主格）」がどのトークンに紐づくかは、スクリーンショットだけでは確定できない。実際の対象トークンの参照（ref/tokenId）、候補ID、候補説明の生成経路を特定するまでは、誤りと断定しない。
- EPH 1:9–10のどの `Χριστῷ` を対象としているかを特定し、語形・格・句構造・候補分析を再確認する。

### この結果の限界

この追跡は現行の公開データとRegistryの読み取り照合であり、ブラウザで表示される候補を実行再現したものではない。解析器の実出力、StudyPanelの候補選択、説明文の描画経路は未確認。したがって、原因を確定したとは扱わない。


### 追加確認：Χριστῷ（EPH 1:10!12）

現行 `main` の章データで対象トークンを特定できた。

- `Χριστῷ` はトークンID `103814`、参照 `EPH 1:10!12`、形態 `N-DSM`（名詞・与格単数男性）。
- 直前は `ἐν τῷ` であり、対象語は前置詞句 `ἐν τῷ Χριστῷ`（「キリストにあって／キリストのうちに」）の内部にある。
- このトークンに「左方転位（懸垂主格）」を直接付与しているのであれば、語形・構造と整合しない。懸垂主格という分析は主格形を前提とするが、ここは与格形で、前置詞 `ἐν` に支配されている。したがって、まず候補IDと説明文の結合ミス、別トークンの候補流用、または表示対象の取り違えを疑うべきである。
- これは章データから確認できた強い不整合だが、画面に出た候補IDと描画コードをまだ照合していないため、原因が候補生成・選択・表示のどこにあるかは未確定。候補生成段階で主格限定条件が守られているか、UIが対象トークン以外の候補を表示していないかを次に確認する。
