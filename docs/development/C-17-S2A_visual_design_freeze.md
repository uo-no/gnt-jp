## 0. 核心問い

> この画面を初めて見たユーザーが、構文の構造を理解しながら、もっと見てみたいと思うか？

現状の率直な答え：**「構造は見えているが、見てみたいとは思いにくい」**

理由：情報密度が高すぎる。構造の骨格と装飾が同じ視覚的重みを持っている。
何が「主」で何が「従」かが視覚的に明示されていない。

## 1. Executive Summary

### 現状

HDG（階層ダイアグラム）と RK（Reed–Kellogg）の両モードは、**機能的には正確に動作している**。
SR JSON を正しく読み込み、ギリシャ語の構文構造を適切に表現している。

しかし、**初見ユーザーへの訴求力に課題がある。**

HDG は「構造の地図」として機能しているが、視覚的な優先順位付けが欠けており、
10本以上の点線ボーダーが横並びになる複雑文では「迷路」に見える。

RK は「文法の骨格」として潜在的に強力だが、従属節・関係節の扱いが
RK本来の簡潔な線画文法から逸脱しており、美しさが失われている。

### 両モードの最大の共通問題

**補助的な視覚要素（点線ボーダー、ラベルチップ、副詞的）が
主要な情報（テキスト、構造関係）と同じ視覚的重みを持っている。**

### 方向

Phase 2-B では：
- HDG：「階段」から「木」へ。ボーダーの視覚的重みを下げ、テキストと構造関係を前面に出す。
- RK：骨格の純粋さを守る。節ボックスのスタイルを RK 文法のイディオムに近づける。

## 3. Current HDG Diagnosis

### 3.1 全体的な第一印象

**OBSERVED：**
JHN 1:1（シンプルな文）を 1024px で見た場合、
「主節 → 節 → 前置詞句」という3層構造は視覚的に読み取れる。
トークンチップ（角丸ボーダー付きの単語）は最も読みやすい要素。

JHN 1:1 を 390px で見た場合、
3〜4本の青い点線ボーダーが画面幅の大半を占め、テキストが右端に追いやられる。

COL 1:9 を 1024px で見た場合、
10本以上の点線ボーダーが縦に並び、高さ約 6,820px の縦スクロールが発生する。
「迷路」の印象。

### 3.2 視覚的優先順位の問題

**CONFIRMED：全階層が均一な視覚スタイルを持つ。**

- 主節（depth=0）: 左ボーダーなし、テキスト小さめ
- 節（depth=1）: 青い点線ボーダー + ▼ラベル
- 前置詞句（depth=2+）: 同じ青い点線ボーダー + ▼ラベル
- 同格（depth=2+）: 同じ青い点線ボーダー + ▼ラベル

文法的に重要な「主節 vs 従属節」の区別が視覚的に弱い。
ラベルチップ（主語, 述語, 補語）は小さく、灰色で、多数表示される。

### 3.3 強みの発見

1. **トークンチップ**：角丸ボーダー付きの単語表示は、ギリシャ語トークンをはっきりと示す。
2. **同格の横並び表示**（COL 1:1）：同格関係を横に並べるアプローチは直感的。
3. **折りたたみ機能**：深い構造を 91% 圧縮できる。長文では特に価値が高い。
4. **インライン節埋め込み**（JHN 1:6）：単語と節ラベルが横並びになる表現が読みやすい。

### 3.4 問題点の具体的記録

| 問題 | 観察箇所 | 重大度 |
|---|---|---|
| 点線ボーダーが多すぎる | COL 1:9 (10+本), EPH 2:1 | 高 |
| 全階層の視覚的重みが同一 | JHN 1:1 〜 EPH 2:1 全て | 高 |
| 前置詞句が独立ブロックとして余分なインデントを生む | COL 1:1, JHN 1:3 | 中 |
| ラベルチップが多数表示され読み疲れ | 全ての複雑文 | 中 |
| 主節ラベルが目立たない（小テキスト） | 全文 | 中 |
| 390px で点線ボーダーが画面幅の大半を消費 | JHN 1:1 @ 390px | 高 |
| ▼ インジケーターが小さく目立たない | 全文 | 低〜中 |

## 5. HDG: MUST KEEP / SHOULD KEEP / SHOULD REMOVE / HARMFUL

### MUST KEEP

| 要素 | 理由 |
|---|---|
| トークンチップ（角丸ボーダー付き単語） | 最も読みやすい要素。ギリシャ語トークンの識別に不可欠。 |
| 折りたたみ機能（▼/▶） | 複雑文の視認性を 91% 改善。ユーザーがナビゲートする主要手段。 |
| 左ボーダーによるインデント | 階層構造の表現に不可欠。ただし視覚的重みを下げる余地あり。 |
| 同格の横並び表示 | 同格関係の直感的な表現として機能している。 |
| インライン節埋め込み（単語 + ▼節） | 節の文脈を保ちながら構造を示す。 |

### SHOULD KEEP

| 要素 | 理由 |
|---|---|
| 役割ラベルチップ（主語, 述語, etc.） | 文法的役割を示す唯一の明示的ラベル。ただし表示サイズ・頻度の調整余地あり。 |
| 主節ヘッダー（主節ラベル） | 文の起点を示す。ただし視覚的強調が必要。 |
| 接続詞のインライン表示（そして, また） | 文間の関係を示す。 |

### SHOULD REMOVE

| 要素 | 理由 |
|---|---|
| 深い階層での全ボーダーの均一スタイル | 深さが増すほど視覚的ノイズが増加。深いレベルは細く/薄くすべき。 |
| 前置詞句ブロックの余分なインデント | 前置詞句の「ブロック化」はインデントレベルを消費しすぎる。前置詞句内のトークンだけを字下げすれば十分。 |

### HARMFUL

| 要素 | 理由 |
|---|---|
| 深い階層での点線ボーダーの青の濃さが均一 | COL 1:9 では10本の等価な青線が並び、構造の軸が見えなくなる。視覚的ヒエラルキーを完全に破壊している。 |
| 展開時のラベルチップの過剰繰り返し | 8つの節がそれぞれ「主語/述語/補語」を全部表示すると、ラベルが本文を圧倒する。コンパクトな表示が必要。 |

## 7. HDG Visual Principles

### アイデンティティ文

> **「ギリシャ語の節構造を、折りたたみ可能な深度マップとして読める」**

### 原則

1. **テキスト・ファースト。** 構造線は補助であり、主役ではない。トークンチップが常に最も目立つ要素であること。
2. **深さに応じた視覚的減衰。** depth 0 は明確、depth 1 は中程度、depth 2 以深は細く薄く。全階層を同じ重みで描かない。
3. **折りたたみを標準として設計する。** 複雑な文は折りたたんだ状態が「デフォルト」の読み方。展開は探索的な行動。
4. **役割ラベルは必要最小限。** 同じ節内で主語・述語・補語を全部ラベル表示するより、役割が自明なケースはラベルを省く。
5. **構造線は骨格のみ。** 前置詞句・同格の「ブロック化」は廃止し、親子関係をインデントで表現する。

---

## 8. RK Visual Principles

### アイデンティティ文

> **「ベースラインと線が、文の骨格を即座に視覚化する」**

### 原則

1. **線画の純粋さを守る。** RK は「線で文法を描く」手法。ボックスは線を殺す。節は接続線で示し、枠線は使わない。
2. **骨格を常に見えるようにする。** 主節のベースライン（主語 | 述語 | 目的語）はスクロールしても見えるべき。
3. **節の視覚的表現を RK イディオムで統一する。** 従属節・関係節・分詞節は、ベースライン上に「L」コネクタで接続した独立ベースラインで表示する。
4. **ラベルは最少化。** 骨格の位置（主語が左にある）が役割を示す。重複するラベルは省く。
5. **修飾の斜線を特別扱いする。** 斜線は RK の代名詞。この要素の可読性を最優先で保護する。

## 9. 共有要素（HDG と RK で統一するもの）

| 要素 | 方針 |
|---|---|
| トークンのフォントサイズ・書体 | 統一。どちらのモードでも同じ文字の読みやすさ。 |
| 文の区切り（1:1 / 1:2 などのラベル） | 統一。節参照の表示方法。 |
| 折りたたみ後の「...」または要約表示 | 将来の課題だが、両モードで共通の設計が必要。 |
| 接続詞の表示（そして, また） | 統一。主節間の論理接続を示す。 |
| モードが違っても同じデータを使う | SR JSON は共通。レンダラーが違うだけ。 |

| 要素 | HDG | RK |

## 11. Before → After Vision

### HDG: Before → After（最低 5 点）

#### Before 1: 全階層が同じ太さ・色の点線ボーダー
**After 1:** depth に応じてボーダーの不透明度を下げる（例：depth 1 = 40%, depth 2 = 25%, depth 3+ = 15%）。
最深部のボーダーはほぼ消え、構造の軸（depth 0-1）だけが目立つ。

#### Before 2: COL 1:9 は 10 本以上の等価な点線が横並び
**After 2:** 深い節を折りたたんだ「要約行」をデフォルト表示にする。
初期状態では主節だけが展開されており、ユーザーが能動的に掘り下げる。

#### Before 3: 前置詞句がブロックとして独立しており、余分なインデントレベルを消費
**After 3:** 前置詞句はブロックを廃止し、前置詞トークンとその目的語を同じ深さのグループとして表示。
ボーダー1本分の深さを削減。

#### Before 4: 役割ラベルチップ（主語/述語/補語）が全ての節で全て表示
**After 4:** コンパクトモードでは述語のみ表示。主語・目的語は hover/tap で表示する。
または主節のみ全ラベル、従属節以深は述語のみ。

#### Before 5: 390px で点線ボーダーが画面幅の 30-40% を消費
**After 5:** モバイルではインデントの単位幅を縮小（例：1024px: 1.5rem/level → 390px: 0.75rem/level）。
または depth 2 以深ではボーダーの代わりに左側の細い帯（2px solid）のみ残す。

#### Before 6: 主節ラベル（主節）が小テキストで目立たない
**After 6:** 主節ヘッダーを強調表示（例：背景色かボールドラベル）。
節の起点が明確になることで、ユーザーが文の構造のどこから読めばよいかがわかる。

---

### RK: Before → After（最低 5 点）

#### Before 1: 従属節・関係節が青い点線ボーダーのボックスに入る
**After 1:** 節ボックスを廃止。各節はベースラインとして描画し、親ベースラインからの「L」コネクタで接続する。
RK 本来の「線で示す」イディオムに統一する。

#### Before 2: 内容節がベースライン上に外枠ボックスを重ねる
**After 2:** 内容節も独立したベースライン行として描画。
ボックスは廃止し、内容節ラベルと L コネクタで親との関係を示す。

#### Before 3: 副詞的 ラベルが密集表示（EPH 2:1 等）
**After 3:** 副詞的 ラベルを省略。斜線の角度と接続位置から「修飾する要素への接続」が自明なため、
ラベルは不要と判断する。必要な場合は hover で表示。

#### Before 4: 複雑文で節の視覚的区別が弱い（全て同じスタイルのボックス）
**After 4:** 節の種類（従属節/関係節/分詞節/内容節）を、ラベルの色または書体ウェイトで区別する。
節構造のラベルだけが色を持ち、テキストは黒単色を維持する。

#### Before 5: 390px で主節ベースラインが画面幅を超えることがある
**After 5:** 主節ベースラインを垂直スタック表示にフォールバックするか、
横スクロール領域を明示的に設ける（scroll-indicator を表示）。

#### Before 6: RK と HDG の「節ボックス」が視覚的に区別できない
**After 6:** RK では節ボックスを廃止することで、HDG との視覚的差別化が自然に生まれる。
HDG はブロック（折りたたみ可能な矩形領域）、RK は線（ベースライン + 接続線）という対比が明確になる。

## 12. Responsive Design Principles

### 1024px 以上（デスクトップ）

- HDG：最大5〜6レベルの深さまで展開可能。全機能フル表示。
- RK：主節ベースラインが全幅に展開。従属節パネルが横並びに並ぶ余裕あり。

### 768px（タブレット縦）

- HDG：インデント幅を 20% 縮小。ボーダーの視覚的重みが 1024px より自然に下がる。
- RK：主節ベースラインが768px幅に収まるか確認が必要。COL 1:1 では問題なし（OBSERVED）。

### 390px（モバイル）

- HDG：インデント幅を 50% 縮小（1024px 比）。depth 3 以深は折りたたんだ状態をデフォルトとする。
- RK：各節パネルを縦積みで表示。横スクロールを許容する箇所を明示する。
- 両モード共通：タップ領域を最低 44×44px 確保（折りたたみラベルを含む）。

## 14. Risks

### R-1: RK の節ボックス廃止による視覚的断絶

節の区切りがボックスに依存していた場合、廃止後に節の境界が曖昧になるリスク。
**軽減策：** L コネクタのスタイルを強化し、境界を線で明示する。先にスタイル適用後のスクリーンショットを評価してから確定する。

### R-2: 前置詞句ブロック廃止の影響範囲

前置詞句ブロックが何層もネストしている場合（COL 1:9 等）、廃止後の見た目が破綻するリスク。
**軽減策：** 前置詞句ブロックのみ CSS クラスを追加し、既存の `hdg-clause--pp` クラスにスタイルを絞って変更する。

### R-3: モバイルでのデフォルト折りたたみ

現在の JS 実装は展開状態がデフォルト。初期状態を折りたたみにする場合、JS 変更が必要になる可能性。
**軽減策：** Phase 2-B では CSS のみで対応範囲を限定する。JS による初期状態制御は Phase 2-C に延期する。

### R-4: CSS 変更が RK レンダラーに予期せず影響する

HDG の `.hdg-clause` スタイル変更が RK の `.dg-view` に影響しないかを確認する必要がある。
**軽減策：** Phase 2-B 実装後、必ず RK の回帰スクリーンショットを取得して確認する。

## 15. Design Freeze Decision

> **「ギリシャ語の節構造を、折りたたみ可能な深度マップとして読める」**

- モバイル最優先：390px で使えない機能は設計の失敗と判断する

**Phase 2-B の実装範囲：** CSS のみ。JS・SR JSON・dg-engine.js 変更なし。
