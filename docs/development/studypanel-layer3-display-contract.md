# StudyPanel 第3層の表示契約と整理順

- 状態: 第3層入口・入れ子開閉の整理は実装済み。意味分類の全体再配置と全語の意味監査は継続中
- 作成日: 2026-10-23
- 前提: `docs/development/studypanel-layer3-information-audit.md`、`docs/specs/LAYER_ARCHITECTURE.md`、PR #241 の代表語ブラウザ検査
- 目的: 情報資産を削除せず、観察事実・解釈候補・判断根拠・参照資料が混ざらない最小限の表示構造を定義する。

## 1. 設計判断

第3層を複数のカードや独立した小パネルへ分割しない。本文中心の画面を維持し、情報の種類ごとに見出し・順序・開閉の役割を分ける。**表示上の区分は意味上の区分を明確にするためのもので、候補の確度を装飾で示すためのものではない。**

- 既存の「詳しく見る」操作で単語詳細に入った後、第3層の情報を無差別にすべて前面へ出さない。
- 第3層の詳細資料は、必要な読者が明示的に開いて確認できる構造を目標とする。
- 画面内に開閉を多重にネストしない。まず第3層全体を任意閲覧にし、その内部は短い区分見出しで整理する。
- Desktop / Mobile で同じ意味分類を使う。表示密度や操作方法の違いは許容するが、同じ情報が片方だけ消える場合は仕様に理由を記録する。
- 空の見出し・空スロット・実際には描画されない機能をユーザーに見せない。
- 辞書・構成的な語義説明・形態情報・用例・出典データは、見た目の整理を理由に削除しない。

## 2. 情報の分類と推奨順序

第3層の中では、次の順に並べる。各項目はデータがある場合のみ表示し、値がないことを「否定された事実」として表示しない。

### A. 原文から確認できる情報

**内容:** 形態情報、見出し語（Lemma）、辞書引き用識別子（Strong）。

- 形態情報は本文・形態データから確認できる観察事実として扱う。
- Lemma と Strong は語の同定・検索用情報であり、文中の機能や意味の結論として表示しない。
- Strong は技術識別子なので本文より目立たせない。Desktop への追加は今回の整理だけでは決めず、別途必要性を判断する。
- 形態の生コードを一般読者向けの解釈文に混ぜない。人間向けのラベルと元データの追跡性を両立する。

### B. 文法・統語の分析と判断根拠

**内容:** 実際に成立した分析候補、候補を区別する本文上の手掛かり、必要な文法用語・Wallace 等の参照。

- 「観察された形」と「その形から可能な分析」を別の文章・ラベルで扱う。
- 候補名だけを並べない。候補が成立する条件と、候補間の違いを確認できる場合に限って説明する。
- 根拠は当該箇所の語・句や構造に結びつける。解析器のスコア、一般的な文法規則、単に文法書が存在することを、その節の解釈の証明として扱わない。
- 未発火・未対応・未確認のシグナルは根拠として表示しない。
- Layer 2 にすでにある短い読書メモを長文で再掲しない。ここでは技術的な根拠と参照先を優先する。

### C. 語義・語彙資料

**内容:** 構成的な語義説明・語源メモ、Abbott-Smith 辞書全文、必要に応じて用例への導線。

- 構成的な説明と辞書本文は役割が違うため、両方を保持する。
- 構成的な説明では、語源的事実・共時的な語義構成・この文脈での解釈を混同しない。
- Abbott-Smith の語義候補を、文脈で採用すべき意味として自動確定しない。
- 辞書の全文を短い読書メモに複製しない。短い読書メモは本文の理解、辞書は語が取り得る意味・用法の確認を担う。
- 辞書全文が長い場合でも内容を削除せず、必要時に展開して参照できる形を優先する。

### D. コーパス・外部資料への導線

**内容:** 同じ語・構文の用例検索、使用傾向への検索ツール導線、実際に稼働している研究リンク。

- 使用傾向は StudyPanel 内に複製せず、既定の検索ツールを参照先とする。
- 用例は実際の文脈を比較する資料であり、頻度統計や類義語分類と同じ情報として扱わない。
- 現在マークアップを生成していない Research Links は、表示されている機能として説明しない。再接続する場合はリンクの出典・対象・存在を検証する。
- LN 由来の関連語・意味グループ表示は、権利・精度の確認が済むまで停止を維持する。

## 3. 表示構造の提案

目標とする構造は以下のとおり。これは実装済み状態の説明ではなく、今後の変更に対する設計契約である。

1. 単語詳細画面の読書支援（Layer 2）は現行の責務を維持する。
2. 第3層の入口は一つにまとめ、詳細資料を任意に開けるようにする。
3. 開いた第3層内では、A「原文から確認できる情報」→ B「文法・統語の分析と判断根拠」→ C「語義・語彙資料」→ D「コーパス・外部資料への導線」の順に配置する。
4. A〜D は重いカードにせず、簡潔な区分見出し・余白・細い区切りで意味を示す。
5. 区分内の個別項目は、内容の長さと必要性に応じて表示する。辞書全文のような長い資料は区分内で必要時に展開できるようにし、短い観察事実まで細かく折りたたまない。
6. Desktop / Mobile では同じ区分順を目標とする。画面の狭さで同じ配置が難しい場合も、情報の分類・出典・意味を変えない。
7. Morphology の現在の直表示は代表語テストで確認済みだが、これを維持するか第3層全体の入口に統合するかは、変更前後の画面密度・既存の「詳しく見る」導線との関係を確認してから実装する。いきなり形態区画だけを別の折りたたみにしない。

## 4. 今回は変更しないもの

- Abbott-Smith 辞書全文、構成的な語義説明、形態・見出し語データ、用例・研究資料データの削除。
- Layer 2 の読書メモの文章生成・解析ロジック。
- 形態・統語データ自体、Wallace の分析結果、原文データの変更。
- LN 関連語・意味グループ表示の再有効化。
- Desktop と Mobile の全機能の機械的な同一化。
- Strong の Desktop 表示追加。
- 全語に対する意味解釈や候補の自動確定。

## 5. 実装前に必要な確認

1. 代表語を最低3種類確認する: 通常の形態情報がある語、Lemma/Strong や辞書情報が欠ける語、構成的な語義説明と辞書全文がともにある語。
2. Desktop 1280×900 と Mobile 390×844 で、第3層の入口を開閉したときの画面密度、スクロール位置、単語選択変更、URL復元を確認する。
3. 第3層を開いた状態で A〜D の順序を確認し、空見出し・空区画・重複ラベルが出ないことを検査する。
4. Layer 2 の読書メモと Layer 3 の統語根拠が同じ結論文を繰り返していないか、少なくとも代表例で照合する。
5. 辞書全文と構成的な語義説明の双方が残ること、Mobile の非同期辞書注入が遅延時・語の切替時にも正しい対象語へ紐づくことを確認する。
6. 上記を満たした小さな UI 実装 PR を作り、既存ブラウザ回帰テストを実行する。設計変更と資産削除を同じ PR に混在させない。

## 6. 実装状況（2026-10-23）

### 完了した範囲

- PR #257: Desktop / Mobile の第3層入口を「単語を詳しく調べる」に統合。Abbott-Smith 辞書全文と構成的な語義説明を保持。
- PR #259: 第3層内部の候補・根拠・候補比較の nested disclosure を通常表示に変更。候補文や根拠文を削除せず、Layer 3 renderer 内に `details/summary` が残らないことを browser test で確認。
- PR #259 の VR-5 browser inventory と evidence-note regression は Desktop 1280×900 / Mobile 390×844 で成功。PR #258 で監査履歴を更新。
- マージ後の PR #258 の初回検査では `check-old-paths` が成功。VR-5 と Cloudflare Pages はその時点では実行中であり、最終結果をこの記録だけから成功と断定しない。

### 未完了の範囲

- この変更は情報の配置・開閉構造の整理であり、全語の意味分析や根拠の意味的妥当性を検証したものではない。
- 全語・全候補について、候補の成立条件、実際に一致したシグナル、該当する語句・節との対応を個別に精査する必要がある。
- Layer 2 読書メモと Layer 3 の説明が同じ結論を繰り返していないか、語義の語源的説明と共時的意味が混ざっていないかは、全体監査として継続する。
- 欠落データを「根拠がない」と誤って表示していないか、辞書全文・形態・Lemma・Strong・出典リンクの保持を異なるデータ状態で確認する。
- 実装前チェックリストの代表語テストは現状5例の browser target（JHN 3:16 の4語と JHN 15:27 の1語）。これを全語監査と同一視しない。

## 7. 次の監査順序

1. `scripts/studypanel-evidence-first-audit.cjs` と `scripts/syntax-evidence-gating-regression.cjs` の出力を確認し、失敗・警告を「形態矛盾」「シグナル未成立」「候補の説明不足」「データ欠落」に分ける。
2. 監査で指摘された候補を、本文トークンと実際の `signals_matched` / `signals_missing` に紐づけて検証する。候補の存在だけを根拠に表示しない。
3. 代表例と境界例を PC / Mobile で確認し、Layer 2 と Layer 3 の重複およびデータ欠落時の表示を点検する。
4. 原因が解析器・レジストリ・表示文言・データソースのどれかを区別し、原因に応じて別々の小さな変更にする。文言だけで根拠の弱さを隠さない。
5. 変更後は既存 VR-5 と browser tests を実行し、変更記録に検査対象・件数・限界を記す。

## 8. 完了条件

- 事実・分析候補・判断根拠・参照資料の区分が文言と配置から判別できる。
- 同じ説明の重複を増やさず、辞書全文・構成的語義説明・形態情報などの研究資産を保持している。
- 存在しない機能の見出し、空の区画、未確認の根拠がユーザーに表示されない。
- Desktop / Mobile の表示差は、意図的な差と未対応を区別して記録されている。
- 代表語のブラウザ検査と既存回帰テストが通り、変更前後の表示を比較できる。
