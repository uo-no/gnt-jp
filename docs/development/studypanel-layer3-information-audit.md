## 1. 結論

Layer 3 は削除対象ではなく、辞書・形態・用例・出典などの研究資産を保持するための「必要時に深掘りする層」である。改善の中心は、情報量の一律削減ではなく、**Layer 2 が担う短い読書支援と、Layer 3 が担う検証可能な詳細資料を分け、同じ説明を二重に語らないこと**にある。

今回の静的監査で整理できた原則は次のとおり。

1. **本文から直接確認できる事実**（形態・見出し語・識別子など）は、推論を加えず詳細層で参照できるようにする。
2. **辞書の語義候補・用法・用例**は残す。ただし辞書の語義を、その節で採用すべき意味として自動的に確定しない。
3. **文法・統語の根拠**は、Layer 2 では本文に結びつく短い説明、Layer 3 では必要時に確認できる詳細な手掛かり・参照資料として分担する。
4. **コーパス上の使用傾向**は、個別節の解釈と混同しない。頻度や共起は判断材料であり、当該箇所の意味を単独で確定しない。
5. **出典・研究リンク**は根拠の追跡経路として保持するが、リンクが存在すること自体を当該解釈の証明として扱わない。
6. **権利・精度を確認できていない意味グループ表示**は、既存データを削除せず、確認が済むまでユーザー向け表示を再開しない。
7. モバイルとデスクトップの機能差は、直ちに不具合と見なさない。既存仕様で意図的な差とされた項目は、その理由を維持しつつ実装を再確認する。

## 2. Layer 2 / Layer 3 の境界

| 情報の役割 | Layer 2「理解する」 | Layer 3「さらに調べる」 |
|---|---|---|
| 本文の観察 | この節で確認できる具体的な語形・語順・つながりを短く示す | 必要時に形態詳細や構造データを参照する |
| 解釈候補 | 実際に成立し得る候補と、読み方の違いを自然な日本語で示す | 候補の技術的な分類名・詳しい根拠・文法書への参照を調べる |
| 判断基準 | 候補を区別するため本文のどこを見るかを具体的に示す | 判定に使われたシグナル、該当する語・句、参照資料を確認する |
| 語彙 | 文脈での読みを理解するための最小限の語義 | 見出し語、辞書の語義候補、語義構成、用例を調べる |
| 使用傾向 | 必要なら文脈理解に関わる要点だけを短く扱う | コーパスの傾向・出現例・検索への導線を保持する |
| 出典 | 読書を止めない範囲で必要な出典を示す | 辞書・文法書・研究資料への参照をまとめる |

**重複判定の基準:** 同じ単語や文法現象を扱うだけでは重複ではない。Layer 2 が「この本文をどう読むか」を助け、Layer 3 が「根拠資料やデータを自分で確認する」役割を果たすなら共存できる。両方が同じ結論文を繰り返す場合は、短い本文理解の説明を Layer 2 に置き、詳細な資料・観察可能なデータを Layer 3 に残す。

## 4. 重複・混同リスク

### 4.1 Layer 2 の読書メモと辞書

- **残すもの:** Layer 2 の短い文脈説明、Layer 3 の Abbott-Smith 全文、必要な構成的語義メモ。
- **避けるもの:** 辞書の説明をほぼそのまま読書メモにも載せること、辞書の複数語義を文脈で選別せずに「この節の意味」として表示すること。
- **基準:** 読書メモは当該箇所の読みを助ける。辞書は語が取り得る意味・用法を確認する。両者は情報源と目的が異なる。

### 4.2 Layer 2 の判断基準と Layer 3 の統語根拠

- **残すもの:** Layer 2 の「どの語・句との関係を見るか」「候補ごとに何が異なるか」という具体的な案内。
- **Layer 3 に置くもの:** 実際に成立したシグナル、形態・構造の詳細、Wallace の参照先。
- **避けるもの:** Layer 2 と Layer 3 に同じ結論を長文で繰り返すこと、シグナルの名前が登録されているだけで実際に根拠が成立したと見せること、解析器のスコアを正解確率として表示すること。

### 4.3 使用傾向・類義語比較・用例

- 使用傾向、同じ語の用例、意味が近い語は、いずれもコーパスに関する情報だが同一ではない。
- 使用傾向は分布の概要、用例は実際の文脈、類義語比較は語間の関係を扱う。
- それぞれの役割を保ち、同じ頻度・同じ説明を複数箇所に複製しない。
- 類義語・意味グループ表示は、権利・精度の確認が終わるまで再開しない。既存データの存在を表示許可とみなさない。

### 4.4 Desktop / Mobile の違い

現行仕様では Morphology は両方にあり、Lemma / Strong は Mobile の詳細内、Dictionary / Usage Trends / Research Links は Desktop の研究機能として配置されている。これは過去の設計で意図的な責務分離とされた差であり、ただちに欠落・不具合と判定しない。

今回の対応では機能を機械的に同一化せず、各項目の役割と現行の非搭載理由を明示する。表示の現状が仕様と一致するかは、次のコード・ブラウザ確認で再検証する。

## 5. 根拠・解釈・資料の表示契約

Layer 3 の詳細表示を実装・再確認する際は、各情報を次のいずれかに分類する。

1. **観察事実:** 語形・形態・語順・参照データ・コーパス統計など、元データに照合できる情報。
2. **分析候補:** 文法・統語上成立し得る候補。分類名だけでなく、候補が成立する条件を追跡できること。
3. **判断根拠:** 当該箇所で実際に確認された手掛かり。本文上のどこに当たるかを示せること。
4. **参照資料:** 辞書・文法書・外部リンク。資料の記述と、特定箇所への適用という推論を区別する。
5. **未確定事項:** データ不足、未実装判定、候補間で決め手がない状態。確定した否定結果と同一視しない。

内部スコア・候補順位だけを根拠に、解釈の確実性を断定しない。データがないときは、説明を無理に生成せず非表示または不確定として扱う。

## 6. 既存資産の保持方針

- Abbott-Smith 辞書全文、形態・見出し語データ、構成的な語義説明、用例・研究リンクは、表示整理のために削除しない。
- Wallace などの文法資料は、文法用語を教えるためではなく、読みの根拠を追跡するための参照枠として保持する。
- Reading Support Projection は読み取り専用のデータ射影という責務を維持する。説明文・HTML・表示状態を持たせない。
- ReadingFormatter を自然文生成の単一経路とする既存原則を維持する。
- 未使用 API や非表示データは、不要であることを確認する前に削除しない。
- StudyPanel は選択語に結びつく情報を扱う。段落全体の修辞構造・段落テーマなど、単一語に還元できない情報を第3層へ押し込まない。

## 14. 候補の根拠ゲートに関するコード監査（2026-10-23）

### 確認した事実

- `public/core/syntax-analyzer.js` の正規化後ゲートは、レジストリの `detection.required_signals` が指定されている場合にその一致を必須とする。
- さらに `detection.conditions` が1件以上ある候補については、`signals_matched` が空なら候補を除外する。
- したがって、**条件が登録されていない候補**、または **必須シグナルが設定されていない候補**については、この共通ゲートだけでは「候補固有の十分な根拠がある」ことを保証できない。
- `scripts/studypanel-evidence-first-audit.cjs` は候補ごとの `signals_matched` 件数を集計できるが、`--strict-evidence` を指定した場合に限って、シグナルが一つも一致しない候補を失敗扱いにする。通常実行ではその項目は報告にとどまり、失敗条件ではない。
- `detection.conditions` の存在と `xsc.signals` の存在は別々に管理されている。説明文にある診断基準が、実行可能なシグナルに対応しているかは別途確認が必要。

### 判定

これは直ちにすべての候補が誤っているという意味ではない。問題は、共通ゲートの通過が候補の妥当性を一律に証明するかのように解釈できる点にある。特に意味論的な判断を必要とする分類では、形態・語順のシグナルだけで用法を確定してはならない。

### 次の実装単位

1. レジストリの全タイプを走査し、`detection.conditions`、`detection.required_signals`、`xsc.signals` の有無と対応関係を一覧化する。
2. 「機械的に確認できる条件」と「文脈・意味の人間判断が必要な条件」を分ける。
3. 必須条件がないタイプを即座に一律排除するのではなく、分類の性質と既存の回帰例を確認してから、候補表示を抑制するか「検討候補」として扱うかを決める。
4. strict audit を追加する場合は、既存の全候補を一斉に失敗させるだけのゲートにせず、違反タイプ・該当トークン・欠けた条件を出力する監査として始める。

このコード監査は実装・データ全件を修正したものではなく、次に検証すべきゲート上の限界を記録したものである。


### 14.1 レジストリ全242型の条件ID対応チェック

`public/assets/data/syntax-registry.json` を全件走査し、`public/core/syntax-analyzer.js` の実際の条件解決方法（`detection.conditions.find(c => c.id === signal.id)`）と照合した。

- 対象: 242型。242型すべてに `detection.conditions` が存在し、条件未登録型は0。
- **25型で、合計41件の `detection.conditions[].id` が `xsc.signals[].id` のいずれにも一致しない。**
- この実装ではスコア計算が `xsc.signals` を起点に条件を同一IDで検索するため、不一致の条件は対応するシグナル評価に適用されない。そのシグナルは条件なしとして加点され、条件の意図と実際のスコア計算がずれる可能性がある。
- これは単なる命名上の不一致ではなく、実行コード上の接続不一致である。ただし、不一致の全てを同じ修正で機械的に置換してよいとは限らない。各ペアの意味が同一か、条件を分割・統合すべきかを確認してから直す。

次工程では、25型の各条件とシグナルを1対1で対応付ける表を作り、意味が同一のIDは整合させる。意味が異なる条件は、条件の分割・評価順・加点対象を再設計し、各変更に代表例と反例の回帰テストを付ける。修正前の現状を保存し、候補が増減する箇所を比較するまでは、レジストリを一括置換しない。


### 14.2 直接対応できる条件IDの追加修正

PR #263 の後続監査で、条件IDの重複が3型に残っていたことを確認した。重複IDは `find()` が最初の条件だけを返すため、後から追加した条件が実際の採点に使われない。今回の修正では、同じ意味の条件を統合し、距離条件は一致名詞が存在する場合に限って評価する。

- `genitive.source`: 出所シグナルとのIDを一致させ、分離動詞の条件は加点条件ではなく候補除外条件へ移動。
- `dative.interest_disadvantage`: 逆接・反抗の条件を既存シグナルに接続。
- `participle.substantival`: 冠詞の存在と冠詞との格・性・数一致を、対応するシグナルへ接続。表示ラベルも完全一致を明示。
- `participle.adverbial_temporal`: 無冠詞・一致名詞なしの条件を既存シグナルに接続し、時制条件をアオリスト専用シグナルに置き換え。
- `participle.attributive`、`participle.adverbial_attendant`、`participle.adverbial_causal`: 重複条件IDを統合。
- 回帰スクリプトに条件ID重複の検出を追加。残る未接続は `dative.means` の `substitutable_with_dia` 1件のみ。これは意味置換テストの実装状態を確認する必要があるため、名称だけを変えて解決扱いにしない。

これは条件とシグナルの接続整合性を改善する変更であり、候補の意味的妥当性を全節で保証するものではない。変更後も新約全体の厳格監査とブラウザ回帰を実行する。


### 14.3 手段与格の型固有語彙リストを判定へ接続

PR #264 後の実装確認で、`semantic_substitution_test('διά')` はハンドラー上つねに `false` を返すこと、また `instrumental_noun_lemmas` は `dative.means.detection` 内にあり共通 `shared.lists` には存在しないことを確認した。従来の条件は実行上の意味判定になっておらず、手段名詞シグナルも型固有リストを参照できていなかった。

- `target_lemma_in_type_list(...)` を追加し、評価中の TypeDef にある語彙リストを参照する。リスト未定義・空の場合は一致なしとする。
- `dative.means.instrumental_noun` 条件を、型固有の `instrumental_noun_lemmas` 参照へ接続する。これは語彙的な補助証拠であり、手段与格の意味確定ではない。
- 「διά + 属格で言い換え可能か」は自動テスト済みと扱わず、文脈に即して別途判断する基準として残す。
- 手段与格の優先補正も同じ型固有リストを参照するよう統一し、ROM 3:28 πίστει の回帰テストでシグナル一致を確認する。

この変更はリスト参照と条件接続の修復であって、全新約箇所における意味判定の正確性を保証するものではない。


### 14.4 恒偽の意味判定ハンドラーの使用箇所監査

PR #265 マージ後、`CheckEvaluator` に登録された判定関数とレジストリの条件を横断し、実装が常に `false` を返すハンドラーを棚卸しした。4種類のハンドラーが6条件で使われている。

- `genitive.attributive.adjectival_equivalent`: 対応形容詞の存在判定は未実装。
- `genitive.attributive.semitic_context`: セム語的文体・背景の自動判定は未実装。
- `genitive.epexegetical.namely_substitutable` / `no_possessive_semantics`: 「すなわち」置換可能性や所有関係の意味的排除を自動判定していない。
- `dative.manner.adverb_substitutable`: 副詞への言い換え可能性を自動判定していない。
- `participle.adverbial_causal.logical_context`: 論証的・因果的な談話関係を自動判定していない。

これらは常に偽を返すため、該当シグナルの加点は行われず、意味判定を実施したかのような肯定的証拠にはならない。一方、候補スコアが不足したり、候補に必要な証拠が不足したりする可能性がある。今回は推測的な意味判定を実装せず、未実装条件の各レコードに制約注記があることを回帰テストで保証する。今後の実装は、代表例と反例、節単位の文脈、既存候補の増減比較を伴って個別に行う。


### 14.5 レジストリ判定式と実装ハンドラーの接続監査

PR #266 の恒偽ハンドラー監査に続き、全242統語型の条件・除外条件に記載された判定式を `CheckEvaluator.register` の登録一覧と照合した。現行レジストリでは148種類のハンドラー名が参照され、すべて実装登録と一致している。

回帰テストでは、条件・除外条件の式中にある関数呼び出しを抽出し、登録されていないハンドラーが1件でもあれば失敗させる。これにより、名前の打ち間違い・実装側の改名漏れが、未知の判定として黙って不成立になるリスクを抑える。

この監査が保証するのは「参照名が登録されていること」までである。ハンドラーが意図どおりの文法・意味現象を検出するか、文脈の切り出しが正しいか、候補順位が妥当かは別途、代表例・反例を用いた意味検証が必要である。
