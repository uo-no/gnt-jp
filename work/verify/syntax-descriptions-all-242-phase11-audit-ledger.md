# 第11段階：242型監査台帳と全体整合性チェック

## 目的

第1〜10段階で作成したレビューを統合し、どこまで確認できたか、何が未確認か、何を先に直すべきかを区別する。**「説明文を読んだ」「Wallaceの一般説明を確認した」「Wallaceの該当節と本文例を個別照合した」「アプリの実トークン候補を検証した」は別の完了条件**とする。

対象は `fix/syntax-description-ja-update` ブランチの `public/assets/data/syntax-registry.json`。レジストリ内のドット付き説明型を重複除去して数えた結果は242型。これはこの提案ブランチの値であり、mainや本番稼働中の実装が同じであることを意味しない。

## 2. 以前の段階を見直して判明した不整合

### A. Wallaceの優先順位

第6段階の初稿はSmythをWallaceと並べて主資料のように記載していた。これは修正し、Wallaceを主資料、Smythを補助資料と明記した。第2・第7段階と全体監査文書も同じ方針にそろえた。

### B. 被属性属格の説明文が監査結果と食い違う

第3段階ではローマ6:4 `ἐν καινότητι ζωῆς` がWallace系公開資料とNET Bible注記に例示されていることを確認済みとした。一方、対象レジストリの `genitive.attributed.description_ja` には「ROM 6:4 も例示として未確認」と残っている。これは**実際に修正すべきレジストリの不整合**である。

ただし、採用版のWallaceの当該ページを照合し、正確な節・ページと本文例を確定するまでは、例を確定的な説明文に残す修正は保留する。監査文書だけの更新で、レジストリ本文はまだ変更していない。

### C. 構造分類と意味分類の混在

以下は全体を通して一貫して注意する必要がある。

- 冠詞付き不定詞：構造分類と、主語・目的・時間などの意味機能が重なる。
- 属格絶対分詞：構文の形と、時間・理由などの意味関係が重なる。
- 接続詞／小辞／談話：語の品詞・構文機能・談話機能が同じトークンに重なり得る。
- 形容詞の限定位置と、意味上の限定機能：同じ「限定」という訳語で混同しやすい。
- 動詞の形態・アスペクトと、文脈で解釈される機能：形態のみで意味を確定しない。

同一トークンに複数の軸のラベルが付く設計なら、すべてを「別候補」として順位付けせず、分類軸を分けて表示する必要がある。

## 3. 全体に適用する合格基準

各型は、次の状態を別々に記録する。

- **R1：原典確認** — Wallaceの採用版で該当節・定義を確認した。
- **R2：本文例確認** — Wallaceの例と、採用するギリシャ語本文・訳を照合した。
- **R3：日本語説明確認** — 定義を自然な日本語にし、専門語を説明した。
- **R4：隣接型比較** — 混同しやすい型との違いを、実例に即して示した。
- **R5：実データ確認** — アプリがそのトークンで実際に返す候補と根拠を確認した。
- **R6：UI回帰確認** — 実際のPC／スマートフォン表示と既存機能をテストした。

現時点では、各分類群について重点論点のレビューと文案作成を進めたが、**R1〜R6が全242型で完了したとは主張しない**。特にR5・R6はこの監査文書の作成だけでは達成できない。

## 4. 追加の実装監査（第12〜15段階）

- 第12段階では、`alternatives` が同時候補を直接生成しない一方、`_computeTieBreakScore()` の `specificity_score` を通じて最終スコアに間接影響することを確認した。
- 第13段階では、`has_adjectival_equivalent`、`semantic_equivalence_test`、`semantic_substitution_test`、`context_discourse_type_eq` が常に `false` を返すことをコードで確認した。
- 第14段階の直接ID照合では39件の不一致を検出したが、後続の第16段階で `_BUILTIN_CONDITION_SIGNAL_MAP` と実行時逆引きを照合した結果、39件すべてに同じ型内のフォールバック条件が存在すると判明。したがって「39件が無条件加点される」という当初結論は撤回した。
- 第15段階の初版にあったID修正案は撤回。直接IDの一括置換は行わず、対応条件の意味と実装状態を監査する。
- 第16段階では、フォールバック自体は機能している一方、`participle.adverbial_temporal` の `temporal_tense` 条件が `tense_aorist` シグナルに対応する意味的不一致を確認した。コード修正PR #229 で条件をアオリスト形に限定し、回帰アサーションを追加した。Node.jsテスト未実行のためDraft。
- 第16段階で挙げた常時falseのチェックに依存する型も別途問題として残る。
- PR #219はclosed / unmergedだが、39件のID不一致はmainにも存在するため、PR #219の差分だけの問題ではない。

## 5. 次の実作業順

1. `genitive.attributed` のレジストリ内の古い「未確認」文言を、採用版Wallaceの節・ページを照合したうえで整合させる。
2. Wallaceの節番号が登録された242型を、原典の定義・例示・例外と一つずつ照合し、R1/R2を記録する。
3. フォールバックマップの全対応がテストで維持されることを確認する。39件のIDを機械的に置換しない。
4. PR #229 の回帰テストをCIで実行し、時制シグナルの修正がPASSすることを確認する。
5. 常時falseのチェック関数に依存する分類を特定し、原典上必要な意味判定か、検出器の能力外としてスコアから外すべきか判断する。
6. 修正前後で全NTの候補順位・閾値通過率・同列候補率を計測し、代表例の候補・シグナル根拠を比較する。
7. `alternatives` のタイブレーク影響を別途測定し、分類学上の関連型リストの長さを確度の代理にする妥当性を判断する。
8. PC／モバイルで候補比較、根拠表示、単一候補時の表示、旧読書メモへの回帰を検証する。
9. 監査結果と実装変更を別コミット・別チェック項目として管理する。
