# 第13段階：CheckEvaluatorの未実装判定を実装と照合

## 結論

`public/core/syntax-analyzer.js` の `CheckEvaluator` 登録処理を確認し、レジストリに記録された未実装注記が実装コードと一致するかを照合した。少なくとも次の4チェックは明示的に常に `false` を返す実装になっている。

| チェック名 | 実装結果 | 説明・候補への影響 |
|---|---|---|
| `has_adjectival_equivalent` | 常に false | 対応形容詞への置換可能性を示すシグナルは発火しない。 |
| `semantic_equivalence_test` | 常に false | 「すなわち」置換による意味的同格性の判定は発火しない。 |
| `semantic_substitution_test(prep)` | 常に false | 前置詞句の置換テストによるシグナルは発火しない。 |
| `context_discourse_type_eq(type)` | 常に false | 談話タイプ・文体判定のシグナルは発火しない。 |

この4件は、コード内コメントにも自動判定が困難で安全側に倒すため常に false と記されている。これは例外的な一回の失敗ではなく、明示的な未実装スタブである。

## レジストリとの関係

これらのチェックに依存する型では、レジストリにシグナル名・説明・加点値が記載されていても、そのシグナルによる加点は現在の実装では起こらない。

既に注記されている候補：
- `genitive.attributive`：`has_adjectival_equivalent` と `context_discourse_type_eq` に依存する判定要素。
- `genitive.epexegetical`：`semantic_equivalence_test` に依存する判定要素。
- `dative.reference`：文脈中の見出し語リストを参照する別シグナルもあるため、型全体が未実装なのではなく、特定の意味判定が発火しない。
- `dative.manner`：`semantic_substitution_test` に依存する判定要素。

重要：このことだけで候補全体が無効とはいえない。別のシグナル、ベーススコア、除外条件、後処理もスコアに関与するため、実トークンで候補の `signals_matched`、`signals_failed`、スコアを確認する必要がある。

## 改善方針

1. **根拠表示で未実装シグナルを証拠として見せない。** レジストリ上の文言に存在するだけで、実際に評価されたかのように表示しない。
2. **型の説明文と検出器の能力を分ける。** Wallaceの定義として説明できても、現在の自動判定がその区別を確定できるとは限らない。
3. **自動判定の限界をユーザー向けに正確に表現する。** 「判定済み」「確定」ではなく、必要に応じて「本文の構造から検出した手掛かり」「候補」とする。
4. **将来の実装では根拠付きのデータを使う。** 例えば辞書・語彙リスト・句／節構造・注釈済み本文を使う場合も、誤検出率を測定してから採用する。単純な語彙置換を意味的同値性とみなさない。
5. **回帰テストを先に追加する。** スタブの状態が変わった際に候補順位や表示が変化するため、各チェックのユニットテストと代表トークンのスナップショットを用意する。

## Wallaceを基準とする原典確認について

Wallaceの文法書は分類の定義・用例・識別の手掛かりを確認する主資料であり、`CheckEvaluator` の現状はアプリの実装状態を示す資料である。両者は別の問いに答える。原典で分類が妥当でも、アプリの検出器がその意味関係を自動判定できるとは限らない。

出版社は *The Basics of New Testament Syntax* を *Greek Grammar Beyond the Basics* の縮約版と説明し、各意味分類に定義と識別の鍵があると説明している：
https://zondervanacademic.com/products/the-basics-of-new-testament-syntax

## 範囲

この段階では、CheckEvaluator内で明示的に常に false を返す4チェックを確認した。レジストリ242型の全 `check` 文字列とハンドラーを完全照合したわけではない。次は、すべての登録済みハンドラー、未登録チェック、常時true/falseハンドラー、無条件加算シグナルを機械的に突き合わせ、候補の根拠表示と順位に影響するものを優先順位付けする。

本段階も監査文書のみの追加であり、実行時のコードやレジストリを変更していない。
