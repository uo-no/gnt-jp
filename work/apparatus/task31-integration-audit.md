## 2. _meta 整合性監査

### Phase 1 (_meta 詳細)

```
_meta.additionCount: 1608   tag=添加 実数: 1609   差: 1
_meta.omissionCount:  809   tag=省略 実数:  809   差: 0
_meta.bothCount:        1   (1TI-0014 — 添加＋省略の両方)
additionCount + omissionCount + bothCount = 2418 = entryCount ✓
```

**REVIEW-1** — `_meta.additionCount=1608` と実際の `tag=添加` 1,609件の1差異。  
原因: 1TI-0014 は `bothCount=1` に計上されているが、タグは `添加`（+prefix が先に記述されるため）。算術的には `1608+809+1=2418` で正確。  
影響: UI が `additionCount` を表示すると1件少なく見える。  
推奨: `_meta` に `additionTagCount` を追加するか、`additionCount` を「純粋な添加エントリ数（bothを除く）」と文書化する。  
→ 現時点で表示UIは存在しないため **破壊的影響なし**。

**1-reading 6件（LUK-1050 等）の特殊性:**  
LUK-1050, 1094, 1099, 1124, 1139, 1140 はすべて `WHspur` 付き。`WHspur` は WH が本文の真正性を疑った箇所のマーカーであり、代替読みを示す通常の apparatus エントリではない。lemText が `[...]` 括弧付きで本文に含まれている。**自動生成対象外** — 本文真正性の注記であり、異読の事実記述と性質が異なる。

**`…` 含む 55件:**  
元データ（apparatus.json）自体のテキストが `…` を含む（SBLGNT 校訂者が長い句を省略表示したもの）。Phase 2 の生成ロジックが `…` 含みを除外した理由は「生成時の切り詰め由来の `…` との混同防止」であるが、これらは元データの `…`。  
例: `τὸ … κλασμάτων ἦραν（WH Treg NIV）・ἦραν τὸ … κλασμάτων（RP）`  

**REVIEW-3** — 元データの `…` と生成切り詰めの `…` が外見上区別できない。UI 表示時に読者が「省略された情報がある」と誤認する可能性。将来の Phase 3 で扱う場合、`…` の出典（元データ由来か生成由来か）を `_meta` または別フィールドで区別する方針が必要。
